2.1 The Critical Need for Tools Pillars

Generative models are frozen in time, holding only the knowledge captured in their training data. Tools bridge this gap, serving as an interactive bridge that connects language models with external systems, databases, real-time facts, and actions.

By equipping an agent with tools, you unlock capabilities like adjusting smart home settings, querying transactional databases, booking airline flights, or scraping local weather forecasts to enrich prompt contexts.

2.2 Extensions (Agent-Side API execution) Extensions

An **Extension** bridges the gap between an agent and a live HTTP API endpoint in a standardized way. The agent handles both the parameter generation and the actual API call **directly on the agent hosting environment**.

This is highly resilient compared to custom code parsing: if a user says "book a flight to Zurich" but omits the departure city, custom scripts fail. Extensions teach the model what parameters are required and how to ask clarifying queries to extract missing entities before calling the API.

Code Interpreter: Run Python stochastically

Google offers native extensions like Code Interpreter, letting the agent write and run Python scripts in a sandboxed runtime to solve mathematical or logical requests:

from vertexai.preview.extensions import Extension

# 1. Load native Code Interpreter extension from the Hub
code_interpreter = Extension.from_hub("code_interpreter")

# 2. Execute natural query requesting code execution
query = "Write a python method to invert a binary tree in O(n) time."
response = code_interpreter.execute(
    operation_id="generate_and_execute",
    operation_params={"query": query}
)

print(response['generated_code'])

2.3 Function Calling (Client-Side API execution) Functions

**Function Calling** decouples API execution from the agent. The language model analyzes a set of developer-provided function descriptions, decides which function to trigger, and outputs a structured **JSON payload containing the required arguments**, but **does not make the actual API call**.

The client application parses the JSON payload, executes the API locally, and optionally returns the observation string to the agent. This is preferred in multiple enterprise scenarios:

  • Security Boundaries: The target API lives behind an isolated corporate fire-wall, inaccessible by the agent infrastructure.
  • Granular Control: The developer wants to transform or filter the API payload before letting the model read it.
  • Authentication: Avoids uploading high-clearance OAuth credentials to the agent hosting environment.
  • Asynchronous Batching: Operations take minutes, necessitating a human-in-the-loop validation layer before execution.

2.4 Function Calling Lifecycle & Python Code Code

Consider a travel concierge agent. If a user asks "I'd like to take a ski trip with my family," standard prompts return an unstructured conversational list of cities. With Function Calling, we define a structured schema payload:

# Model-generated Function Call payload:
function_call {
  name: "display_cities"
  args: {
    "cities": ["Aspen", "Park City", "Whistler"],
    "preferences": "skiing"
  }
}

Python Implementation with Gemini 2.0 Flash

Here is how to register a local Python function and capture the model's structured argument predictions:

from google.genai import Client, types
from typing import Optional

# 1. Define local target method and docstrings (Google uses docstrings for schema learning)
def display_cities(cities: list[str], preferences: Optional[str] = None):
    """Provides a list of cities recommended based on preferences.
    Args:
        preferences: User preferences (e.g. skiing, beach, bbq).
        cities: Recommended target cities list.
    """
    return cities

# 2. Instantiate Gemini client
client = Client(vertexai=True, project="PROJECT_ID", location="us-central1")

# 3. Query model, enforcing tool selections
response = client.models.generate_content(
    model="gemini-2.0-flash-001",
    contents="I'd like to take a family ski trip but I'm not sure where to go?",
    config=types.GenerateContentConfig(
        tools=[display_cities],
        automatic_function_calling=types.AutomaticFunctionCallingConfig(disable=True),
        tool_config=types.ToolConfig(
            function_calling_config=types.FunctionCallingConfig(mode='ANY')
        )
    )
)

# 4. Extract generated arguments
call = response.candidates[0].content.parts[0].function_call
print(f"Function: {call.name}")
print(f"Arguments: {call.args}")
# Output -> Function: display_cities, Arguments: {'preferences': 'skiing', 'cities': ['Aspen', 'Park City', 'Whistler']}

2.5 Data Stores (Vector RAG Pipelines) Data

**Data Stores** act as search-engine attachments. They store dynamic documents (PDFs, spreadsheets, website URLs, unstructured text) in a **Vector Database** as high-dimensional mathematical embeddings.

Instead of manual code integration, the agent query is embedded, matched against document chunks via fast algorithms (such as ScaNN), and the semantic text snippets are injected directly into the orchestration loop to ground the model, eliminating expensive retraining cycles.

2.6 Tools Comparison & Selection Guide Guide

Select the optimal tool type based on your architectural dependencies:

Feature Extensions Function Calling Data Stores
Execution Location Agent-Side (Hosted Cloud) Client-Side (Local Server) Agent-Side (Vector Database)
Granular Data Control Low (Direct API bindings) Maximum (Developer-managed) High (Semantic vector chunks)
Typical Use Case Native integrations like Code Interpreter or standard open APIs. Interactions with internal DBs, batch operations, or authenticated loops. Retrieval-Augmented Generation (RAG) over PDFs, logs, or websites.
API Exposure Requirement Requires public internet endpoint. Can reside behind secure firewalls. Requires pre-indexed document collections.
